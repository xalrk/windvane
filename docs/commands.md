# Command reference

Every command takes `-C <dir>` before it to run as if started in that directory, and `--help` after it for its
options. Commands that read state (`status`, `queue`, `watch`, `stats` and so on) cost no tokens.

## Setting up

| Command | What it does |
|---|---|
| `windvane init [dir] [--name N] [--check CMD] [--forge github\|git]` | Set windvane up in a repository: writes `.windvane/` (config, queue, questions, critic scale). |
| `windvane doctor [--clean [--dry-run]]`, `windvane doctor --leaks` | What this machine lacks for windvane (Claude Code logged in and new enough for the session flags, gh, tmux, the phone), with the fix for each; it warns when the temp dir is over 90% full (inodes or space) and names windvane's leftovers there, and says how much of the project's state directory could go (the biggest item named). `--clean` removes the temp leftovers and, for every project whose autopilot isn't running, idle slot worktrees with nothing unmerged, old transcripts and merged tickets' old critic packs ([`[state]`](configuration.md#state)); `--dry-run` lists what would go, with sizes, and removes nothing. With `forge = "github"` it warns when the repository is public, as `.windvane/` is then public too. `--leaks` is `windvane public-check` without `--github`. |
| `windvane public-check [--github]` | What the repository would expose if it went public, read-only, in any git repository. It scans every commit on every branch and tag in one pass, deleted files included: the lines each adds, files named like secrets, commit messages, and personal author or committer emails. It also checks workflows that give a fork's pull request secrets (`pull_request_target`, or `pull_request` with secrets). `--github` also scans the pull requests (titles, bodies, comments, reviews) through `gh`, and checks secret scanning, push protection, existing Actions runs and artifacts, and whether your account keeps its email private. It prints the kind and place (commit, PR number, `file:line`), never the text, so the output is safe to paste. Then it lists what to do, in order. Exits 0 when clean, 1 on a leak or a workflow to fix (GitHub settings warn without changing it), 2 when the scan couldn't finish ([before going public](safety.md#before-going-public)). |
| `windvane install [--yes]` | Add the windvane skill and the mention hook to Claude Code, asking before each change. |
| `windvane uninstall [--yes]` | Remove exactly what `install` added. |
| `windvane phone setup [--server URL] [--token TOKEN] [--no-service] [--revoked]` | Turn on pushes and questions on your phone through ntfy. `--revoked`: the old topics a rotate left on a server of your own have been taken back, so setup stops printing their lines. See [Phone setup](phone.md). |
| `windvane phone off` / `rotate` / `listen` | Turn the phone off; make new topics; act on the phone's replies (what the background service runs). |

## Tickets

| Command | What it does |
|---|---|
| `windvane new <title>` | Write a new ticket file with the next free id. |
| `windvane plan [goal] [--merge] [--no-followups] [--max N]` | A planner session writes up to N tickets (default 6) for the goal (default: config's `goal`) and the critic's follow-up notes, and opens a pull request with them. `--merge` merges them at once; `--no-followups` leaves out the critic's notes. Its branch is `plan-<date>-<time>`; a push the remote refuses twice leaves the plan on a local branch of that name, for you to push. While another plan runs it says so and exits 1. |
| `windvane critic --project [--dims a,b] [--parallel N] [--minutes 60]` | The critic judges the whole project on `main` against `.windvane/CRITIC.md` (a ladder scale): one read-only session per dimension (`--dims` picks some), up to N at once (default: the run's `parallel`), every check answered with evidence for each `no`, joined into one printed report. Its follow-ups an open ticket covers are added to that ticket's notes on `main`; the `new` ones go to the next `windvane plan` or triage. Costs show in `stats` as `critic:project`; refused while a run is on. |
| `windvane critic --project --last` | The latest project verdicts, one line each: every dimension's score, new and covered follow-ups. |
| `windvane periodic <name>` | Run a `[[periodic]]` entry and its `then` chain now, as a run would between tickets; its tickets land where its `land` says. While a run is on, it asks that run for the round at its next gap between tickets instead (an entry only on `main` works too); `--cancel` takes the ask back. A schedule between its windows refuses it: ask during one. |
| `windvane queue` | The queue: the tickets not done yet, in the order they run, the done ones they depend on, then a count of the rest (`--all` lists every ticket); a `requests = true` entry's line counts the untriaged requests. |
| `windvane request "<title>" [--body <file>\|-]` | File a request to windvane itself from any project (a desk session, or a worker: at most 2 per run): `R-NNN.md` in the machine's inbox, `~/.local/state/windvane/_requests/`, with the project's name, commit, role, date and the body (what happened, evidence, what was wanted, the workaround), censored, with absolute paths outside the project and windvane cut. A title close to an open request's joins it (`## Also from <project>`). windvane's own run triages it; the filing project's next `status` shows the verdict once (`R-004 accepted → windvane's T-110`). |
| `windvane request --status` | Every request, newest first, with its verdict (open, accepted → ticket, rejected: why, question: what the triage asks). |
| `windvane request --answer R-NNN "<answer>"` | Answer the triage's question on a request (its push and `status` say so): the answer is added to it and the next run triages it again. A question waits for this; it isn't a phone question. Only the desk answers: a session (a worker too) is refused. |
| `windvane answer <ticket> <answer>` | Answer a ticket's question at the desk: a letter (`windvane answer T-007 B`) or free text in quotes. |
| `windvane preflight [--for 4h] [--json]` | The product questions the next tickets will need, asked now. `--json` prints them for a Claude Code session to ask. |

## Running

| Command | What it does |
|---|---|
| `windvane run --until HH:MM \| --for 6h [options]` | Work the tickets until the deadline (`--until` also takes `"YYYY-MM-DD HH:MM"`). Options below. |
| `windvane run --from <when> --until HH:MM \| --for 6h --detach` | Wait in tmux until `<when>` (HH:MM or `"YYYY-MM-DD HH:MM"`), then run. A start already past starts now; an `--until` before the start is the next day's (`--from 22:00 --until 06:00` runs overnight). |
| `windvane run --daily HH:MM-HH:MM --detach` | Run in this window every day (it may cross midnight), each window a run of its own with its own pushes; typed inside a window, the first runs from now. Between windows it waits without starting sessions. `stop` ends the schedule, `deadline` moves the end of the current or next window, `status` shows `waiting: starts 12:00 (daily 12:00-20:00)`. A reboot ends it. |
| `windvane stop [--now] [--if-running]` | Stop after the current ticket. `--now` kills every session of the run; their worktrees keep the work for the next run. With no run going it says `autopilot isn't running; nothing to stop` and changes nothing (a waiting schedule is still called off); `--if-running` (for scripts and phone hooks) leaves out the second half. Either way it kills the project's [kept jobs](safety.md#kept-heavy-jobs) at once. |
| `windvane deadline <when>` | Move a running autopilot's deadline: `14:00`, `"2026-10-02 09:30"`, or from now, `+90m`, `+2h`. |
| `windvane retry <ID>` | Put a failed or set-aside ticket back in a running autopilot's queue once you've fixed the cause; it starts again between tickets. One that failed at the merge with its approved head unchanged is merged without a worker or review. Refuses a ticket held for another reason, saying what lets it go. With no run going it says what the next `windvane run` does with the ticket, read from a fresh fetch of main: takes it up, or not, because it is merged, parked (delete its `parked:` line on main), has an open question, or waits on another ticket (and what lets that one go when it is parked or asked); an id with no ticket on main is an error. |

Options of `windvane run`:

| Option | Meaning |
|---|---|
| `--detach` | Run in a tmux session (`windvane-<name>`). A driver that crashes there is restarted with the same deadline and what it had done, pushing the error each time; a fourth crash within an hour ends the run. |
| `--parallel N\|auto` | The most tickets at a time (default from config). |
| `--cap`, `--week-cap`, `--ticket-hours`, `--min-slot`, `--answer-wait` | Override the matching [config keys](configuration.md#autopilot) for this run. |
| `--replan N [--goal G]` | When the queue runs dry, plan new tickets, up to N times. |
| `--no-preflight` | Start without asking the next tickets' questions. |

## Watching

| Command | What it does |
|---|---|
| `windvane status [--line [--running]]` | Running or not, what happens to questions now (`questions: pushed to your phone as they come`, or `questions: none pushed until Sun 08:00 (quiet time); workers build their recommendation`), the slots, questions waiting for you, a `held back for <age>, not pushed:` line per change a refused push kept on a local branch (with why and what to do, and its commit subject whole), the log's tail; while one you pushed by hand is listed, it fetches first, so one merged meanwhile (by a squash or rebase merge too) drops off by itself. `--line`: one line, with the held-back count and the oldest one's age; `--running`: such a line for every project whose autopilot is on, from anywhere (the phone's `status`). |
| `windvane overview` | Where the project stands: tickets merged, underway, not started; critic scale health; held-back changes, as in `status`; then `overview_extra`'s output. |
| `windvane watch [-n 30] [-o 6]` | Follow the running sessions live: what each says, the commands it runs, their output (`-o` lines each, 0 hides output). |
| `windvane stats [--days 7] [--by role\|ticket] [--wide]` | Tokens, turns and minutes per role or ticket, from the ledger, costliest first by weighted tokens (cache reads and output priced in), in 100 columns (`--wide` adds each run's starting context and what each turn re-reads, wider than 100 columns); runs that died or were killed for time, orphaned process groups killed, and by ticket the outcome and the cost per merged ticket with and without overhead. See [Token efficiency](tokens.md). |
| `windvane stats --critic [--last 10] [--since <YYYY-MM-DD\|commit>]` | How the critic's scores spread over the last N tickets, and each check's yes rate (first head, any head), naming one to sharpen (always yes) or lower (never yes, except a dimension's top rung, rare by design) and any check id two dimensions share; on an old numeric scale, how often its cap checks were answered and lowered a score; `--since` keeps only verdicts at or after a date or a commit's author time (say, the one that changed `CALIBRATION.md`); then what it bought: which checks sent work back and whether the next head changed the tree or only the pack, the revision rounds' turns and tokens, the reviews that bounced a critic pass, each ticket's first critique against the ones after it (turns, weighted tokens, the checks a re-critique carried over), and the checks that decided nothing. |
| `windvane stats --projects [--since <YYYY-MM-DD>] [--json]` | Every project on this machine side by side, from its state dir and its repo (which each run records as it starts; older state dirs say "repo unknown"), over the last 30 days or from `--since`: tickets merged, failed (with the log's reason) and parked now (with the queue's); each role's share of weighted tokens and its weighted tokens per merged ticket; the critic's first-pass count, median first and final score and final scores on the pass mark, for the tickets it first judged in the window; reviews after a critic pass that still sent work back; check minutes per checked ticket, failed and cut-off checks, and worker minutes in `await`; re-fixes (a merged ticket a later ticket's text names as what it fixes or as broken, read from the words next to its id); and lines added to `CALIBRATION.md`. Then each measure's lowest and highest value and the projects at either end. `--json` gives the same for a session. Reads only: it takes no lock and writes nothing, so a run in another project is never held up. |
| `windvane stats --periodic [--days 7]` | Each [[periodic]] entry's `score=<n>` over time, oldest first, with its last summary. |
| `windvane mode` | How a design question is handled right now: asked, or built provisionally (quiet time). |
| `windvane quiet` | Show the quiet times files (yours and the project's) and what they mean now. See [Quiet times](configuration.md#quiet-times). |

## Measuring windvane

| Command | What it does |
|---|---|
| `windvane bench [--ref HEAD] [--hours 4] [--full\|--small] [--cap N] [--week-cap N]` | Build the seed projects in `bench/` with the real pipeline and score each on acceptance tests no session sees. Per seed: a fresh repo with a local bare remote (`forge = "git"`) and a state dir of its own under `~/.local/state/windvane/_bench/<run id>/<seed>/`, run with `windvane run` for up to `--hours`, the seeds side by side, with the windvane of `--ref` (a detached worktree of this checkout, removed after) and no phone, `gh` or GitHub token; every product question gets its recommendation built. Then the hidden tests run in a scratch clone of each seed's final `main`. Full is every seed and ticket; small (two seeds, three tickets each, the fourth parked) when the latest weekly usage is over `machine.toml`'s `bench_week_small` (75); the first line says which and why (`bench: small (weekly usage 81% > 75%)`). Ends with a table per seed: tickets merged, failed and parked, hidden tests passed per ticket, weighted tokens, API $ and minutes; the sessions are denied the hidden tests by path, and a seed whose run streams name one anyway is marked `contaminated` and not counted. Each seed's record goes to `bench.jsonl` in this project's state dir. A Ctrl-C, SIGTERM or SIGHUP ends every seed run (and its sessions), removes the worktree and says where the logs are; a full run takes hours and spends real usage. |
| `windvane bench --dry-run` | The plan (size and why, the seeds and their tickets) and what earlier runs of that size cost, without running anything. |
| `windvane bench --last` | The latest run's table again. |

## Machine-heavy work

| Command | What it does |
|---|---|
| `windvane heavy [--wait <min>] [--mem <GB>] [--expect <min>] [--measure] -- <command>` | Run a machine-heavy command (engine, render, big build) one at a time on this machine, once `--mem` GB of memory are free (default: the project's `heavy_mem`, else `machine.toml`'s `min_free_gb`), waiting up to `--wait` minutes (default: a session's stop, else `machine.toml`'s `heavy_wait`, 60), then exiting 75 without running it. While it waits on memory it says why, and once that its need is `min_free_gb` when it has none of its own, naming the `machine.toml` it's set in and how to lower it. `--expect` is how many minutes it likely runs: the jobs waiting behind it count that until it has run times of its own. `--measure`, for a command that measures timing (a frame-time or benchmark run): it also waits until the 1-minute load average is at or under `machine.toml`'s `measure_load` (default a quarter of the CPU count), saying `heavy: waiting: load 9.5 (want ≤ 4)` and the three processes using the most CPU, and letting the jobs behind it by meanwhile, for `machine.toml`'s `measure_hold` minutes of that wait (default 20): then it holds the line (`heavy: holding the line for a quiet CPU after 20 min`), since each job it lets by adds load, and the jobs behind it wait, saying which pid holds them up and that `measure_hold` bounds it, until the load is down and it has run. Measurements queued together share that hold: one waiting behind a measurement that holds the line, or next in line while it runs, holds the line at once (`holding the line too, as pid 4242 did`), so the jobs behind them are let by for one `measure_hold` in all, not one each. If the load stays up another `measure_hold` minutes with no heavy job running, the load isn't the queue's: it lets them by again (`heavy: the load stayed up 20 min with no heavy job running: letting other jobs by again`). Every job's output starts with `heavy: load 1.2 at start` and ends with `heavy: load 3.4 at end, 5.1 peak`, so a run on a busy machine shows as one. See [the heavy lock](safety.md#the-heavy-lock). Runs outside the Bash sandbox, whose read-only runtime folder can't hold the lock and whose pid namespace hides the jobs. |
| `windvane heavy --status` | Who holds the heavy lock (pid, command, folder, since when, how long it has run and usually runs: `running 72 min, usually 40`, or `expected 40` from its `--expect`; if stopped with Ctrl-Z, `paused, so everyone waits: resume it with kill -CONT -<pgid>`, waking its whole process group, the command too), or `free`. Then each live waiter in line: its pid, since when, `measuring` for a `--measure` job, what it waits on and the work ahead of it (`about 20 min of work ahead (until about 01:30)`). Each waiter is judged as its own wait judges it. One that every waiter ahead lets by may wait on memory (`waiting for 6 GB, 4.1 free; letting smaller jobs by`) or on load (`waiting for load ≤ 4, now 9.5; letting other jobs by`, or `holding the line` once its `measure_hold` is up). This project's `heavy_reuses` helpers count as free memory for its own jobs. The first such waiter lists the three processes holding the most memory or CPU. One stopped with Ctrl-Z says `paused, so skipped: resume it with kill -CONT -<pgid>`; one behind a `--measure` job holding the line says so. Never waits, takes no lock and no place in line. Runs outside the Bash sandbox, which hides the jobs' processes. |

## Used by the sessions

These are what the autopilot's sessions call; you rarely need them yourself.

| Command | What it does |
|---|---|
| `windvane ci [workflow] [--ref <branch>] [--dry-run]` | Start a GitHub Actions workflow (default: the repo's only one) on the current branch, only if this month's minutes plus its last run's stay within `actions_cap`; prints what's used and what's left. `--dry-run` counts and says, but starts nothing. |
| `windvane check [--lines 60] [--mem GB]` | Run the project's check, reusing a pass recorded for the same git tree. Exits 0 on a pass, 1 on a failure, 75 (`CHECK NOT RUN`) when a `heavy_check` never got the machine. `--mem` (with `heavy_check` only): the free memory this check waits for, over `heavy_mem`. In a session every check runs as the session's bg job `check`, so it (and a heavy check's wait for the machine) outlasts the tool call: still waiting or running after ~9.5 min, it exits 75 saying so, and `windvane await check` gives its result, recorded for the tree (asking again joins the same job, not the queue). A reused pass or no configured check answers at once, even piped. |
| `windvane critic <ticket>` | Have the critic judge a ticket's evidence pack, and print the worker's next step. |
| `windvane bg [--heavy [--mem <GB>] [--expect <min>] [--measure] [--keep]] <name> <command...>`, `windvane bg --cancel <name>` | Start a long command in the background (under the heavy lock with `--heavy`, needing `--mem` GB free, as `heavy` does: a small job left on the default may wait long for memory it doesn't need, and its log says so; likely running `--expect` minutes, waiting for a quiet CPU with `--measure`). A session's job dies with the session; a `--keep` one outlives it: it waits its turn and runs until the run's stop, and the driver holds its ticket (no session, not counted as a partial) until it ends, then resumes it with the job's exit code. See [kept jobs](safety.md#kept-heavy-jobs). `--cancel <name>` ends your own job of that name instead, waiting or running (its whole process group, SIGKILL after a few seconds' grace), frees its place in the heavy queue and leaves `windvane: cancelled` as its log's last line and exit 143; a cancelled `--keep` job no longer holds its ticket. Runs outside the Bash sandbox, where its job would end with the call. Started from a Claude Code session, the job's `$TMPDIR` is the one the session's sandboxed commands get (`CLAUDE_CODE_TMPDIR`, else `CLAUDE_TMPDIR`: Claude Code's `claude-<uid>` dir under the session's TMPDIR), so it reads and writes the same files they do; but a `$TMPDIR/...` typed in the `bg` command line is expanded outside the sandbox, so an argument naming a file (or folder) that exists only on the sandbox's side is refused with the full path to pass instead. `heavy` does the same. |
| `windvane await <name> [lines]` | Wait up to about 9.5 minutes for a `bg` command. While a `--heavy` one is still in the machine's queue it prints `WAITING` and two lines on where it stands now, read as `heavy --status` reads it: who holds the lock, then its own, `now: this job (pid 41, queued at 03:30) is next in line (waiting for 8 GB, 2.4 free; letting smaller jobs by); about 10 min of work ahead`. It prints `RUNNING` while the job runs. Log lines it shows say their age (`log, last said 58 min ago:`), and an estimate that ran out reads `overdue since 03:57`. It prints `DONE` with its exit code and log tail once it ends (exiting 0 whatever that code is). A job whose start was killed before its command ran (no log, no exit) prints `NEVER STARTED <name>` and the `windvane bg` command that starts it again, and exits 3, so it isn't taken for a command that failed. A job an older windvane started before an update is still found when it runs in the caller's worktree; one that can't be tied to it is named in one line, not awaited. Runs outside the Bash sandbox, which hides the job's process. |
